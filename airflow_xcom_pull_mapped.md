# Airflow XCom Pull in Mapped Task Groups

## Context
When working with **Dynamic Task Mapping** in Airflow (especially with nested `TaskGroup`s), downstream tasks often need to consume outputs (XComs) from upstream tasks within the same mapped instance.

Standard `xcom_pull` calls (e.g., `{{ ti.xcom_pull(task_ids='task_id') }}`) often fail or return the wrong data because they do not automatically resolve the specific **map index** of the current task instance. This is particularly problematic when you need to access a specific key from a dictionary returned by an upstream task in a mapped group.

## The Pattern
To correctly retrieve an XCom value for the *current* mapped instance, you must explicitly pass the `map_indexes` argument to `ti.xcom_pull` using `ti.map_index`.

```python
"{{ ti.xcom_pull(task_ids='<full_task_group_path>.<task_id>', map_indexes=ti.map_index)['<key_if_dict>'] }}"
```

### Example Usage
In this example, `stage_new_data` is a mapped task (part of a mapped task group) that needs to pull paths generated by the upstream sibling task `build_paths`.

```python
stage_new_data = GCSToGCSOperator(
    task_id="stage_new_data",
    source_bucket=bucket, 
    # CRITICAL: explicitly passing map_indexes=ti.map_index
    source_object="{{ ti.xcom_pull(task_ids='process_and_log_extracts.atomic_swap_operations.build_paths', map_indexes=ti.map_index)['source_object'] }}",
    destination_bucket=bucket, 
    destination_object="{{ ti.xcom_pull(task_ids='process_and_log_extracts.atomic_swap_operations.build_paths', map_indexes=ti.map_index)['destination_object'] }}",
    move_object=False,
    replace=True,
)
```

## Implementation Details
1.  **`ti` Object**: The `ti` (TaskInstance) object is available by default in Airflow Jinja templates.
2.  **`map_indexes=ti.map_index`**: This argument tells Airflow to fetch the XCom value associated with the same map index as the current running task. Without this, Airflow might return a list of all XComs for that task ID or fail to find the specific value.
3.  **Full Task Path**: deeply nested tasks within TaskGroups require the full dot-separated path (e.g., `process_and_log_extracts.atomic_swap_operations.build_paths`).
4.  **Dictionary Access**: If the XCom is a dictionary (common in PythonOperator), you can access keys directly in the Jinja template (e.g., `['source_object']`).

## Benefits
*   **Correctness**: Ensures mapped tasks access their own specific data, not data from other mapped instances.
*   **Efficiency**: Avoids passing huge lists of data to every task instance; each instance pulls only what it needs.
*   **Readability**: keeps the data flow explicit within the DAG definition.

## Caveats
*   **Typos in Task IDs**: The string passed to `task_ids` must be exact. If you rename a TaskGroup, you must update these strings.
*   **Airflow Version**: This syntax requires Airflow 2.3+ where Dynamic Task Mapping was introduced.
