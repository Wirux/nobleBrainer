# XCom Pull in Mapped Tasks

> [!INFO] Context
> When working with **Dynamic Task Mapping** in Airflow (especially nested `TaskGroup`s), standard XCom retrieval fails because it doesn't automatically know *which* mapped instance's output to pull.

## The Pattern

To retrieve the XCom value for the **current** mapped instance, you must explicitly pass the `map_indexes` argument to `ti.xcom_pull` using `ti.map_index`.

```python
"{{ ti.xcom_pull(task_ids='<task_group>.<task_id>', map_indexes=ti.map_index)['<key>'] }}"
```

## Example Usage

In this example from a generic silver processing DAG, a mapped task (`stage_new_data`) needs to pull specific paths generated by its upstream sibling (`build_paths`) within the same mapped group.

```python
stage_new_data = GCSToGCSOperator(
    task_id="stage_new_data",
    source_bucket=bucket,
    # Pull 'source_object' from the 'build_paths' task for THIS mapped index
    source_object="{{ ti.xcom_pull(task_ids='process_and_log_extracts.atomic_swap_operations.build_paths', map_indexes=ti.map_index)['source_object'] }}",
    destination_bucket=bucket,
    destination_object="{{ ti.xcom_pull(task_ids='process_and_log_extracts.atomic_swap_operations.build_paths', map_indexes=ti.map_index)['destination_object'] }}",
    move_object=False,
    replace=True,
)
```

## Key Components

1.  **`ti` Object**: The TaskInstance object, available globally in Airflow Jinja contexts.
2.  **`map_indexes=ti.map_index`**: This is the critical argument. It filters the XCom query to return only the value produced by the task instance with the matching map index.
3.  **Full Task Path**: For tasks inside `TaskGroup`s, you must provide the full dot-notation path (e.g., `parent_group.child_group.task_id`).

> [!WARNING] Caveats
> *   **Airflow Version**: Requires Airflow 2.3+ (Dynamic Task Mapping).
> *   **Task ID Accuracy**: The `task_ids` string must be exact. If you rename the TaskGroup, this string *must* be updated manually.
